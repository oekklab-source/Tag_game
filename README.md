# 3D Chase Game（Godot 4 / WebSocket オンライン鬼ごっこ）

PC がホスト（WebSocket サーバ）、Web ブラウザがクライアントとして参加する
3D 三人称視点のオンライン・チェイスゲーム。マリオ風のカラフルでポップな
160×160m のマップに、6種類のギミックを配置している。

## ルール

- ラウンド開始時に全員から **Runner（逃げ）1人** をランダム選出。残り全員が **Hunter（鬼）**
- 開始直後は **8秒のヘッドスタート**: 鬼（人間・CPU とも）は動けず、Runner だけ逃げられる
- ヘッドスタート後 **3分** 逃げ切れば Runner の勝ち。
  Hunter が Runner に **実際に触れる**とタッチ成立で Hunter の勝ち
  （距離判定ではなく Area3D の接触判定。実効の接触距離は約 1.1m）
- **鬼は Runner の位置を既定では一切知らない**（CPU も同じ）。**目線に入った時だけ**分かる:
  - 視認の条件は 距離 **48m 以内** かつ 水平視野 **100°以内** かつ **障害物に遮られていない**こと。
    背後は完全な死角で、6m の壁は視線を切る
  - 視認している鬼は Runner の**正確な位置**を追う
  - **誰か一人が視認した瞬間、Runner がいる「ゾーン」だけが全鬼に共有される**。
    見失っても最後の目撃ゾーンは **20秒** 残り、その後 `NO INTEL` に戻る
- **索敵情報の非対称**:
  - Hunter は共有された**ゾーン名と色だけ**。`SPOTTED` / `LAST SEEN ○○ 12s` / `NO INTEL` の3状態。
    方向・距離・マーカーは無し
  - Runner は **全体の2Dマップ**（右上）で鬼全員の位置が見え、最寄りの鬼への
    **赤矢印＋距離**、鬼が近いと画面端が赤く脈打つ**危険表示**、
    そして見られている間は **SPOTTED! 警告**が出る
- 鬼の人数による速度補正: 3人以上 = **95%** / 5人以上 = **90%**（それ以下は 100%）
- **役割は準備中に選べる**: 逃走者の枠は1人だけで、`R` で立候補すると前の立候補者は
  鬼に戻る（奪い合い）。ホストは `Tab` で誰にでも付け替えられ、一巡すると「未定」に戻る。
  未定のまま開始すると従来どおりランダムに選ばれる
- 結果表示の5秒後は**準備中に戻って止まる**。役割を選び直す時間を作るため、
  次のラウンドはホストが Enter を押すまで始まらない
- **ソロモード**: ホスト1人だけで Enter を押すと自分が Runner になり、**CPU の鬼が6人**出現する。
  CPU は情報が無い間はマップ全体を**巡回して探し**、通報があればその**ゾーンを捜索**し、
  自分の目で見つけたら**追跡**する（人間の鬼とまったく同じ情報しか持たない）

## マップ

160×160m（`x, z ∈ [-80, +80]`）を **3×3 の9ゾーン**に分割。
ゾーンごとに地面の標高が違う段丘構造で、隣接ゾーンはスロープ11本で繋がっている。

| # | 位置 | 名前 | 地面 | 目玉ギミック |
| --- | --- | --- | --- | --- |
| 0 | 北西 | CLOUD DECK | 8m | 上空を周遊する動く床 |
| 1 | 北 | PIPE YARD | 2m | マンホール（SKY STEPS 行き） |
| 2 | 北東 | BLOCK PLAZA | 4m | ？ブロック密集 |
| 3 | 西 | GARDEN GREEN | 1m | 回転床の飛び石 |
| 4 | 中央 | CASTLE COURT | 0m | ハブ。マンホール（CLOUD DECK 行き） |
| 5 | 東 | BOOST CIRCUIT | 1m | ダッシュパネルの周回コース |
| 6 | 南西 | SPRING VALLEY | 3m | ジャンプ台群 |
| 7 | 南 | LIFT HARBOR | 0m | 昇降リフトと上空シャトル |
| 8 | 南東 | SKY STEPS | 6m | 高台。マンホールとジャンプ台で登る |

マップは手書きの `.tscn` ではなく、[scenes/world_data.gd](scenes/world_data.gd) の
**定数テーブルから [scenes/world_builder.gd](scenes/world_builder.gd) が生成**する。
レイアウトを変えるときは `world_data.gd` だけを編集すればよい
（ゾーン判定・HUD のミニマップ・スポーン位置もすべてここを参照している）。
乱数は装飾配置のみで固定シードなので、全ピアが同一の形状を構築する。

### ゾーンのテーマ

各ゾーンには専用の構造物と色がある。**「何を置くか」だけがデータ**（`ZONE_THEMES` の
重み表と `ZONE_LANDMARKS` の目印1個）で、**「どこに置くか」は配置側**（`_build_props`）が
決める。十字通路・スポーン地・隙間といった不変条件は配置側が持ち続けるので、
テーマ表を編集してもレイアウトの安全性は壊れない。

構造物は4種類（`Prop`）: 城壁 `WALL` / 塔 `TOWER` / 配管 `PIPE` / コンテナ `CRATE`。
どれも**地面から6m以上まで途切れずに塞ぐ凸の塊**であること。視線レイは y=0.85 と
y=1.55 にあるので、宙に浮いた傘や細すぎる柱を混ぜると
「画面では壁越しに見えているのに `can_see` は false」になって破綻する。

天面は 60°超のキャップ（円錐 or 屋根型の笠木）で終える。歩行面にならないので
Recast が構造物の上に孤立したナビ島を作らない。加えて `TopGuard` を必ず載せる
（丸い形は傾斜だけでは防げない。球面の頂点付近は接線角が連続的に 0 になり、
半径3mのドームなら直径4.2mの「立てる平地」が天辺にできる）。

床の柄はゾーンごとに変える（`_zone_pattern`）。4x4 ピクセルのテクスチャを
ワールド空間トライプラナーで貼るので、UV 無しで全ての床とスロープに模様が繋がる。

## ギミック

いずれも**触れるだけで発動**する（専用の操作キーは無い）。逃走者・鬼の双方が使える。

| ギミック | 効果 |
| --- | --- |
| マンホールワープ | 光の柱に入るとペアの柱から飛び出す。進行方向へ軽く逃げる。CPU は近道になる時だけ入る |
| ジャンプ台 | 真上に打ち上げ（頂点 約8.6m）。高いゾーンへの主要ルート |
| ダッシュパネル | 2.5秒間スピード1.6倍＋矢印方向へ蹴り出し |
| 動く床 | 昇降リフト／上空シャトル。乗ると一緒に運ばれる |
| 回転床 | 円周上を運ばれる（自分の向きは変わらない） |
| ？ブロック | アイテムを1つくれる。12秒で復活。CPU は反応しない |
| 滑り台 | 一方通行の下り。最大18m/s まで加速する。**登れない** |
| バンパー | 触れると外向きに弾き返す丸い障害物。ゾーンごとに最大2個 |

### 滑り台と、高いゾーンの出入り

高所2ゾーン **CLOUD DECK(8m) / SKY STEPS(6m)** は、対角に置かれた「空の島」。
出入りの経路は意図的に絞ってある。

| 向き | 手段 |
| --- | --- |
| 登る | ジャンプ台（各ゾーン2基）／マンホール |
| 降りる | 滑り台（各ゾーン2本）／ジャンプ台の着地口から飛び降り |

このために **滑り台を架けた境界のスロープは撤去し**（`_build_ramps`）、
**落差3m以上の縁には高さ2.5mの柵を立てている**（`_build_parapets`）。
柵の開口は滑り台の入口とジャンプ台の着地点だけ。
どちらも無いと「歩いて降りる」「どこでも飛び降りる」で代替でき、滑り台の意味が消える。

ジャンプ台の着地点にも口を空けているのは、塞ぐと登坂ルートが死ぬため
（GARDEN GREEN からの打ち上げの頂点は CLOUD DECK の床のわずか 1.6m 上）。
そこからは飛び降りもできるが、1箇所に限られ、着地しても速度は歩行のまま。
滑り台は 18 m/s 出るので価値は残る。

**登れないのは幾何ではなく速度の制御で保証している。** 走路の傾斜は 26.6° で、
45°（`floor_max_angle`）を超えていないので普通に接地でき、歩行モーションも横操作も生きる。
代わりに走路の上にいる間は進行方向の速度が最低 3.5 m/s へ毎フレーム引き上げられ、
ジャンプも封じられるので、登ろうとするとズルズル押し戻される。
走路は**直線の1枚板**。以前はカーブさせていたが、分割したセグメントの継ぎ目で足が引っかかった。

**CPU の経路はナビリンクで通している。** 滑り台の幾何は Platform レイヤーにあり
ナビメッシュに焼かれない（焼くと「登れる」と誤判断して詰む）ので、
代わりに `NavigationLink3D` を張ってある。

- 滑り台のリンクは**一方通行**（`bidirectional = false`）＝ CPU も降りることしかできない
- マンホールのリンクは双方向。これが CPU にとって唯一の登坂ルートになる
- マンホールのリンクの端点はマンホールの中心ではなく「相手と反対側の足元」に置く。
  中心に両端点を置くと CPU は相手のフタの上へ直接移動してしまい、途中でフタを
  踏まないのでワープが発動しない。この位置なら端点から相手へ一直線に歩くと
  必ずフタの上（判定 半径1.1m）を通る

### ワープの出口が真上だけだと無限ループする

出口の速度を垂直成分（`up_vel`）だけにすると、無操作で入った場合そのまま
真上に飛んで**入った時と寸分違わぬ xz 座標へ落ちてくる**。出口は
`EXIT_HEIGHT`(1m) 分だけ相手のフタの上に浮いているので、落下の途中で
相手の判定（半径1.1m・高さ1.2m）をもう一度通過する。
`warp_lock`(0.9s) は再突入を短時間だけ防ぐが、往復にかかる時間の方が長いため、
**ロックが切れた瞬間にまた入ってしまい A↔B を無限に往復する**。

直すには出口で「進行方向」へ軽い水平の勢いを足せばよい。マンホール自体には
向きの情報が無い（`MANHOLES` にヨー角は無い）ので、**入った瞬間の
実速度**（動いていなければ向いている方向）を使う。これなら常に
入った時とは違う場所へ着地し、ぴったり同じ座標に戻る経路が構成的に無くなる。

```gdscript
var vel_flat := Vector3(body.velocity.x, 0.0, body.velocity.z)
var dir := (vel_flat.normalized() if vel_flat.length() > 0.5
    else -body.global_transform.basis.z)
body.warp_to(pair.global_position + Vector3(0, EXIT_HEIGHT, 0), EXIT_UP,
    dir * EXIT_FORWARD)
```

**これだけでは直らなかった。** `warp_to()` は `global_position` を直接動かすが、
`is_on_floor()` はその時点では**まだ warp 前の接地状態を指したまま**
（次に `move_and_slide()` が走るまで更新されない）。次の物理フレームの先頭で
その古い `true` を信じて地上の移動制御に入ると、無入力時は目標速度＝ゼロへ
即座に上書きされ、**足した水平速度がその場で消える**。実測でも frame 0 で
横方向 `-2.57, -3.06` が付いていたのに frame 1 では `0, 0` に戻っていた。

滑り台の `SLIDE_GRACE` と同じ考え方で `warp_grace`（0.2秒）を設け、
その間は `is_on_floor()` の値に関係なく空中と同じ制御にしている
（`player.gd` / `cpu_hunter.gd` とも同じ構造）。

`tests/manhole.tscn` が「無操作で入っても出口の水平速度がゼロでない」
「その向きが進行方向と一致する」を検証している。

`tests/map_connectivity.tscn` がこの構造を自動検証している（全ゾーン間の到達性、
マンホールのリンクを切った時に「登れる経路 0 / 降りられる経路 7」になる非対称、
そして下記の走路の貫通チェック）。

### 土管をやめてマンホールにしたら、ナビメッシュの前提が変わった

もとは高さ2mの土管だった。土管は `collision_layer = 1`(World) の `StaticBody3D`
なので、`NavigationMesh` の `geometry_parsed_geometry_type = 1`（静的コライダのみ）
に拾われ、**ナビメッシュに実測 2.3m の穴を空けていた**（半径1.5 + `agent_radius` 0.45
+ セルの量子化）。CPU の経路はその穴を迂回して引かれていた。

マンホールはフタが地面と面一で、**静的コリジョンを一切持たない**。
そのため穴が空かず、CPU も人も上を普通に歩ける。代わりに2つ変わった。

1. **踏んだら即ワープになる。** 土管は「口に飛び乗る」必要があったが、
   マンホールは走り抜けただけで発動しうる。判定は口の半径2.1m から
   **フタの上だけ（半径1.1m・高さ1.2m）**へ絞ってある
2. **`PIPE_LINK_OFFSET`(3.0) の存在理由が変わった。** 以前は「穴に繋がらないから
   ずらす」だったが、いまは「端点を中心に置くと CPU が相手のフタの上へ
   直接移動してしまい、途中でフタを踏まないのでワープが発動しない」から。
   相手と反対側の足元へ逃がしておけば、端点から相手へ一直線に歩く経路が
   必ずフタの上を通る

地面と同じ高さになると遠くから見つけられなくなるので、モデル
（`assets/props/manhole.glb`）に**天へ伸びる光柱・回転リング・舞う結晶**を
含めてある。光柱は 14m — 最高ゾーン（SKY STEPS 6m）＋柵 2.5m より高く、
雲（高度 40m〜）には届かない高さ。

### マンホールの演出だけは RPC で配る

このプロジェクトの規約は「効果は権威ピア・演出は全ピア」で、`spring_pad` は
`Area3D` の `body_entered` が全ピアで発火することを利用して RPC 無しで演出している。
マンホールだけは `question_block` と同じ RPC 方式にしてある。理由は2つ。

1. 発動できるかの判断材料（`warp_lock` / `_cpu_wants`）は**権威ピアにしか無い**。
   各ピアが独立に判断すると、フタが開くピアと開かないピアが出る
2. **出口側のフタ**は、出現位置（`EXIT_HEIGHT` 1m）が判定の外に出ると
   `body_entered` が鳴らない。`pair` を明示的に叩く必要がある

ただし発火元はホストではなく**そのボディの権威ピア**（クライアントでありうる）
なので、`question_block` の `@rpc("authority", ...)` ではなく
`@rpc("any_peer", "call_local", "reliable")` を使う。

フタの開閉は `AnimationPlayer` ではなく Tween でやる（`spring_pad` / `bumper` と同じ）。
そのために `build_manhole.py` は **`Lid` の原点をヒンジ（枠の内縁）に置いて**
書き出しており、Godot 側は `rotation.x` を回すだけで開く。
Blender の +Y が glTF 変換で Godot の -Z に来るので、ヒンジは `z = -1.12` に立つ。

### 光柱は深度を書かない

`scenes/beacon.gdshader` は `blend_add, unshaded, cull_disabled, depth_draw_never`。
`depth_draw_never` が要点で、加算合成でも深度を書くと**光柱の向こう側にいるキャラや
地形が光柱に隠されて消える**。書かなければ光として重なるだけになる。
`cull_disabled` は、光柱が上下のフタを持たない開いた筒で内側も見えるため。

結晶は MultiMesh ではなく1メッシュに結合されているので `INSTANCE_CUSTOM` が使えない。
代わりに頂点の**方位角**を位相に使い、`build_manhole.py` 側が黄金角(2.4rad)で
並べることで結晶どうしの位相が重ならないようにしてある。

### 走路のキープアウトは「点」ではなく「面」

滑り台の走路の下や中に壁やプロップが生えると、当然そこを滑れなくなる。
最初は走路の中心線（入口・出口・出口の先の3点）を配置済みリストへ足していたが、
**点と点の間、つまり走路の中ほど14mが素通しだった**ため壁が貫通していた。

走路は必ず X か Z のどちらかに平行なので（`_slide_path` は直交軸の座標を動かさない）、
平面視の**軸平行な矩形1枚**で厳密に表せる。`_slide_rects` がこれを作り、
遮蔽ブロック・バンパー・プロップの配置が `_hits_keepout` で面同士の判定をする。

高さは見ない。走路は入口の 8m から出口の 0m まで降りてくるので、
「下をくぐれる高さが保証できる区間」がそもそも存在しないため。

手置きのゾーン目印（`ZONE_LANDMARKS`）は条件に関係なく必ず建つので、
場所を選ぶ側より先にキープアウトへ積んでおく（`_landmark_rects`）。
でないとバンパーに位置を先取りされてめり込む。

## アイテム

？ブロックから手に入り、**1個だけ持てる**（新しく取ると上書き）。**E キー / マウス右ボタン**で使う。

| アイテム | 効果 |
| --- | --- |
| ロケット | 前方へ大きく飛ぶ。ジャンプでは届かない距離を一気に詰める/離す |
| バナナ | 足元の後ろに置く。踏んだキャラが1.5秒転倒する（CPU も踏む） |
| ブロック設置 | 目の前に15秒だけ壁を作る。**視線も通行も塞ぐ** |

置き物（バナナ・ブロック）の生成は必ずサーバが行う。プレイヤーの位置権威は
クライアント側にあるが、クライアントが自前で生成しても `MultiplayerSpawner` を
通らず他ピアへ同期されないため。

**アイテムを使える条件と、置き物を生成できる条件は必ず一致させること。**
`GameManager.request_drop` だけが `PLAYING` 限定だった頃は、ラウンド外で
？ブロックを取って使うとアイテムだけ消えて何も置かれなかった
（？ブロック側には状態の判定が無く、いつでも配ってしまうため）。
`tests/item_drop.tscn` がラウンド外・ラウンド中の両方で置けることを検証している。

## 高い場所について

**壁の上には立てない。** 天面が 63° の屋根型になっていて滑り落ちるうえ、
稜線に乗った場合に備えて弾き出す領域も重ねてある
（カプセルが尖った稜線の真上に来ると接触法線が真上になり、
面の傾斜に関係なく立ててしまうため。凸形状では原理的に避けられない）。

**ジャンプは無い。** 自力で跳ぶ手段を持たないので、高さの移動はすべて
スロープ・ジャンプ台・滑り台・マンホール・リフトのどれかを通る。
どこを登れて / 降りられるかがマップの設計だけで決まり、抜け道が生まれない。

## 操作

| 入力 | 動作 |
| --- | --- |
| W / A / S / D | 移動 |
| マウス | カメラ（クリックでキャプチャ、Esc で解放） |
| Shift（押しっぱなし） | ダッシュ（速度1.5倍、スタミナ消費） |
| Space | **ダイブ**（前方へ低く飛び込む） |
| E / マウス右ボタン | アイテムを使う（`A` は左移動に使っているため `E`） |
| R | 逃げる役に立候補 / 取り消し（**準備中のみ**。全員が押せる） |
| Tab | 逃げる役を順送りで指名（**ホストのみ・準備中のみ**） |
| Enter | ラウンド開始（**ホストのみ**。1人なら CPU 戦） |

準備中は**ロビーのパネルをマウスでも操作できる**（一覧の行をクリックして指名、
ボタンで役割切り替えとラウンド開始）。キーは同じことができる近道。

### 役割の選択

逃走者は常に1人なので、状態は「今 誰が立候補しているか」の peer_id **1個**しか持たない
（`GameManager.wanted_runner`。`-1` = 未定）。`R` で立候補すると前の立候補者は自動的に
鬼へ戻るので、2人が同時に逃走者になることが原理的に起きない。

ホストの `Tab` は一巡に**「未定」も含める**。全員鬼＝ランダムに戻す選択肢を残すため。
選択は準備中のロビーに一覧で出て、立候補中の人だけ体色が緑になる。

### UI

表示は日本語。Godot の既定フォントは日本語のグリフを持たず、そのままだと
UI が全部豆腐（□）になるので **`ui/fonts/` に丸ゴシックを同梱している**
（M PLUS Rounded 1c、OFL。JIS 第一水準にサブセット済みで 1.6 MB）。
テーマ `ui/pop_theme.tres` の `default_font` から全 Control に効く。

待機中は画面中央にロビーのパネルを出し、マウスを解放する。
`hud.gd` の `_ignore_mouse()` は「HUD に操作できるウィジェットは一つも無い」
前提でマウス入力を全部無視させているが、ロビーだけはその対象外にしてある
（ラウンド中は `visible = false` なので、視点操作を奪う問題は起きない）。

### 通信の版数

`GameManager.PROTOCOL_VERSION` を接続直後に突き合わせ、食い違ったら
はっきりエラーを出して切断する。**RPC の引数を足す/減らす/並べ替えたら必ず上げること。**

Godot の RPC はメソッド名と引数の個数が両ピアで一致している前提で、食い違うと
`Method expected N argument(s), but called with M` で黙って落ちる。
症状は「つながってはいるのに状態が同期しない・ラウンドが始まらない」で原因が非常に
分かりにくい。**Web 版はブラウザが古いビルドをキャッシュするため特に起きやすい**ので、
片方だけ更新した心当たりがあるときはまず版数（タイトル画面の右下・ロビーの見出し）を見る。

接続直後に突き合わせて、食い違えば**参加側は理由を出してタイトルへ戻り、
ホスト側はロビーに警告を出してその参加者を切断する**。

> **参加リンクで遊ぶときの落とし穴 その1：前回の Godot が residual で残っている**
>
> `create_server(9999)` に失敗しても、以前は **world.tscn へ移ってから**失敗していた。
> 画面はゲームなのに誰ともつながらず、しかも `leave()` を `_ready()` の途中で呼ぶので
> `Parent node is busy adding/removing children` になってタイトルにも戻れなかった。
>
> 悪いのはここから先で、**9999 を掴んだままの古い Godot はまだ生きている**。
> 参加リンクはその古いホストにつながるので、
> **「参加しても始まらない／同期しない」** という症状になる
> （Enter を押しているのは新しい方のプロセスで、参加者がいるのは古い方）。
>
> 今は `start_host()` が **シーンを移る前に** `TCPServer` でポートを試し、
> 埋まっていればタイトル画面のまま理由を出す（`tests/host_conflict.tscn` が回帰を見ている）。
> それでも掴んでいるプロセスは自分では消せないので、**タスクマネージャで
> 残っている Godot を閉じること**。
>
> **その2：GitHub Pages のビルドが古い**
>
> `tools/serve.ps1` が出す参加リンクは `https://<owner>.github.io/<repo>/?s=<トンネル>` で、
> **ブラウザが読むのは GitHub Pages に置いてあるビルド**（＝最後に `main` へ push した内容）。
> 一方ホストはエディタの手元のコードで動く。つまり **push せずにコードを変えると、
> ホストだけ新しく参加者は古いまま**になり、RPC が噛み合わなくなる。
> ゲームのコードを変えたら `main` へ push して Actions のビルド完了を待ち、
> 参加者にはブラウザをスーパーリロード（Ctrl+Shift+R）してもらうこと。

### ダイブ

ジャンプの代わりの、鬼が距離を詰めて捕まえるための手段。
前方へ 12 m/s（ダッシュの1.14倍）で飛び込み、当たり判定も体ごと前へ出る。

踏み切った後は**着地まで軌道を変えられず、着地後 0.55 秒は起き上がりで動けない**。
外すと大きな隙になるのがリスクで、逃走者は横へ避ければ引き離せる。
浮くのは 0.46m だけなので、段差を越える手段にはならない（柵は 2.5m ある）。

逃走者も同じダイブを使える。鬼だけの技にすると Space に何も割り当たらず、
また追う側だけが加速手段を持つ形になるため。

### キャラ同士の重なり

プレイヤーと CPU 鬼は `collision_mask` に `Character` を含むので互いに衝突するが、
**CharacterBody3D 同士は `move_and_slide()` で相手を押せない**。そのため重なると
自力では抜けられず、次の2つが起きる:

- 横に重なる → 双方が相手を壁と見なして**楔状に固まり動けない**
- 相手の頭に乗る → `is_on_floor()` が true になって**重力が止まり、空中で静止したまま
  落ちてこない**

`CharacterSeparation`（`scenes/character_separation.gd`）が水平の分離速度を明示的に
足してほどく。あわせて「他キャラの頭の上は床として扱わない」ので、乗った側には重力が
効いたまま横へ滑り落ちる。分離速度は `carry_velocity` と同じく
**足して動かして引く**（velocity に残すと毎フレーム蓄積して吹き飛ぶ）。

湧き位置も黄金角で振り分けて、そもそも重ならないようにしてある。ここで注意が要るのは
**MultiplayerSpawner のスポーン状態は「送り手が権威を持つ同期ノード」の分しか配られない**
こと。プレイヤーの権威は本人にあるため、ホストが選んだ座標は本人にだけ届かず、
本人の画面では原点に出て先に居た人と重なっていた。ラウンド開始時と同じく
`GameManager.place_player` で本人に伝えて `teleport()` させている。

`tests/separation.tscn` と `tests/net_roles.tscn` がこの2つを検証している。

空中では水平方向の慣性が残る（入力しなければ減速しない）。
ジャンプ台やダッシュパネルで得た勢いはこの仕様に依存している。

接地中も、通常速度を超えている間は目標速度で上書きせず 10 m/s² で減速する。
これが無いと滑り台の出口・ダッシュパネルの蹴り出し・ロケットの着地で得た勢いが
着地の1フレームで消える。

## 歩行モーション

### 足がすべらないようにする

再生倍率は `速度 / NATURAL_SPEED` で決める。`NATURAL_SPEED` は
「Run を等倍で再生したときキャラが実際に歩く速度」で、**手計算せず
`tests/anim_stride.tscn` で実測する**（ボーンのローカル軸は Blender と glTF で
向きが変わるため、ポーズの角度から求めようとすると必ず間違える）。

テストは Run を1周期ぶんコマ送りし、接地している側の足が胴体に対して
後ろへ流れた距離を積む。それがそのまま「胴体が前へ進むべき距離」になる。

以前はこの値が 10.5 m/s ということになっていたが、実測は 1.33 m/s だった。
つまりアニメが **約8倍遅く**再生されていて、足は盛大にすべっていた。
歩幅そのものも足りなかったので、`tools/blender/build_fallguy.py` の Run のポーズを
前脚は膝を伸ばして遠くへ、後脚は蹴り切って後ろへ流すように直し、
1周期 1.06m -> 1.93m（2.42 m/s 相当）まで広げてある。

通常速度 7.0 m/s では足すべりはゼロになる。ダッシュ 10.5 m/s だけは
必要な倍率 4.35 が上限 3.6 を超えるので約2割すべる。
全高1.74mで脚が0.56mしかないキャラを 10.5 m/s で走らせている以上、
歩幅は骨の長さで頭打ちになる。完全に比例させると毎秒11歩になって脚がブレるので、
そこは上限で止めている。

### ガタガタさせない

**描画フレームごとの位置差分から速度を出してはいけない。**
`_process` は描画レートで回るが `global_position` が変わるのは `_physics_process`
（60Hz）なので、描画が物理より速いと「前フレームから動いていない」フレームが混ざる。
差分をそのまま速度にすると、そこで速度0と判定されて Idle に落ち、
次のフレームで Run に戻る。これが歩きがガタガタに見えていた原因。

- 権威ピア: `_physics_process` の中で `velocity` と `is_on_floor()` を実測する
- 他ピア: その値（`sync_speed` / `sync_air`）をそのまま受け取って使う
- さらに時定数で平滑化し、Idle と Run の境目にはヒステリシスを入れる

**速度を「同期位置が前回からどれだけ動いたか」で割り出してはいけない。**
それは移動時間ではなく**パケットの到着間隔**を測っているのと同じで、
LAN なら等間隔に届くので動くが、インターネット越し（トンネル経由の Web
クライアント）だと到着がまとまったり途切れたりするだけで速度が乱高下し、
脚が止まったり痙攣したりする。速度を正確に知っているのは権威ピアだけなので、
`sync_speed` として素直に配るのが一番確実で安い（float 1個 + bool 1個）。

`tests/net_anim.tscn` が2ピアを実際につないで検証する:

```sh
godot --headless --path . res://tests/net_anim.tscn -- host
godot --headless --path . res://tests/net_anim.tscn -- client 127.0.0.1
```

## ブラウザ（Web エクスポート）での確認（同一 LAN 内）

1. **Web** プリセットは [export_presets.cfg](export_presets.cfg) にコミット済み
   （**Thread Support はオフ**。オンにすると COOP/COEP ヘッダが必要になる）。
   export テンプレートが未導入ならエディタの案内に従ってダウンロードする
2. `export/web/` へエクスポートし、http で配信:
   ```sh
   python -m http.server 8000 --directory export/web
   ```
   ※ ページを **https で配信すると ws:// 接続がブロック**されるため、必ず http（localhost/LAN 内）で配信する
3. PC 側でゲームを起動（エディタ実行で可）し **HOST**
4. スマホ/別PCのブラウザで `http://<PCのIP>:8000` を開き、ホストの IP を入力して **JOIN**
5. つながらない場合は Windows ファイアウォールで **ポート 9999（TCP）** を許可する

描画は `gl_compatibility` 固定。装飾は MultiMeshInstance3D 3本に集約してある。

フレームレートが足りない場合は、`world.tscn` の **`glow_enabled` を最初に切る**のが
一番効く。次が `Sun` の `shadow_enabled`。

ドローコールは `tests/screenshot.tscn` が固定アングルで実測する
（`Performance.RENDER_TOTAL_DRAW_CALLS_IN_FRAME`）。ゾーンをテーマ化した際の実測値:

| アングル | テーマ化前 | 現在 |
| --- | --- | --- |
| 俯瞰 | 337 | 229 |
| 滑り台 | 436 | 271 |
| 地上 | 365 | 219 |

内訳は3つ:

1. **構造物の描画を MultiMesh に集約**（`WorldBuilder.Batch`）。約110個のメッシュが17本になる
2. 笠木・柵・バンパー・レールを**影パスから外す**（`_no_shadow`）。
   外してよいのは「真下に必ず影を落とす本体がある物」と「背が低くて影が足元にしか
   出ない物」だけ。視線を切る 6m のプロップ本体は外さない（長い影が距離感の手がかりになる）
3. 当たり判定の無い茂みを廃止（バンパーに置き換え）

### MultiMesh 集約と「見た目と当たり判定の一致」

描画コストに乗るのは `MeshInstance3D` だけなので、**当たり判定の `StaticBody3D` +
`CollisionShape3D` は1個ずつ残したまま、メッシュだけを集約できる**。

一致を保つ仕掛けは「集約するかどうかに関わらず、両方を `_solid()` の中で
同じ `pos` / `size` / `rot` から作る」こと。集約の都合で片方だけを触れる場所は作らない。

形は**単位サイズ**（一辺1 / 直径1 / 高さ1）で持ち、大きさはインスタンスの拡大率で作る。
そうしないと大きさ違いが全部別グループになって集約にならない。ただし2つ除外がある:

| 形 | 集約 | 理由 |
| --- | --- | --- |
| 箱・角柱 | する | 法線が軸に沿っているので、軸方向に拡大しても向きが変わらない |
| 円柱 | する | 側面の法線は水平なので、縦の拡大に影響されない |
| **円錐** | **しない** | 側面の法線が斜めなので、非等方に拡大すると陰影が変わる。屋根として大きく映るので見た目を優先した |
| カプセル | しない | 全高に半球が含まれ、非等方に拡大すると形が崩れる |

円錐を集約から外す判断は、集約の前後で同じアングルを描画して画素を比べて決めた
（`tests/screenshot.tscn`）。差分は屋根の面にはっきり出ていて、外すと消えた。

バンパーも集約しない。触れた時の潰し演出でメッシュを個別に縮める必要があるため。

### 装飾の揺れ

**規約: 当たり判定のある物は `GameManager.world_time`、装飾だけの物はシェーダの `TIME`。**

動く床・回転床は全ピアで位相が揃っていないと乗った位置がずれるので `world_time` を使う。
雲は当たらないので同期が要らず、[scenes/decor_float.gdshader](scenes/decor_float.gdshader)
の頂点シェーダで動かす。MultiMesh 数百個の transform を毎フレーム CPU で
書き換えるのは Web で高くつくため。

- `render_mode world_vertex_coords` で `VERTEX` をワールド座標にする。
  モデル空間のままだとインスタンスの拡大率が揺れ幅に掛かり、大きい雲ほど大きく揺れる
- 揺れの位相は `INSTANCE_CUSTOM` でインスタンスごとにずらす。
  1つの雲を作る3つの球には同じ位相を入れる（バラけると雲に見えない）
- `custom_aabb` を広げる。フラスタムカリングは元の AABB で判定するので、
  広げないと揺れて外へ出た分が画面端で急に消える

**`TIME` と `INSTANCE_CUSTOM` が Compatibility レンダラで効くことは実測で確認済み**
（`tests/screenshot.tscn` の `decor wobble` / `instance phase`）。
時間差の比較だけでは足りない。`INSTANCE_CUSTOM` が読めていなくても全部の雲が
揃って動いてしまい、画は変化するため。位相を 0 に潰して画が変わるかまで見ている。

## インターネット越しに遊ぶ（外部の友達と）

自宅PCがホストのまま、**Cloudflare Tunnel** で公開する。費用は0円で、
ルータのポート開放も Windows ファイアウォールの設定も要らない
（`cloudflared` は外向き接続しか張らない）。

```text
[友達のブラウザ] --https--> GitHub Pages   (ゲーム本体。固定URL)
        |
        `--- wss://xxxx.trycloudflare.com --> [Cloudflare] --> cloudflared --> Godot ws://localhost:9999
                                                                               (自宅PC・ホスト)
```

### なぜトンネルなのか

- **TLS**: Web ビルドを置ける無料ホスティングはすべて https 固定で、https ページから
  `ws://` への接続は mixed content としてブロックされる。**外部公開には `wss://` が必須**。
  トンネルが TLS を終端するので、Godot 側に証明書を持たせずに済む
- **NAT 越え**: 日本の主要 ISP（v6プラス / OCN バーチャルコネクト等）は
  ポート開放できない・制限される回線が多い。ポート開放を前提にすると
  「動く人と動かない人がいる」構成になる

### Web ビルドの配信（初回だけ）

`main` に push すると [.github/workflows/web-build.yml](.github/workflows/web-build.yml) が
Web ビルドを作り、成果物だけを **`web-build` ブランチへ force push** する。
GitHub Pages はそのブランチを見てデプロイする。以降は**push するだけで公開が更新される**。

1. `winget install --id Cloudflare.cloudflared`
2. main を push して Actions を1回通す（`web-build` ブランチができる）
3. リポジトリの **Settings > Pages** で
   - **Source: Deploy from a branch**
   - **Branch: `web-build` / `/ (root)`**
   を選んで Save
4. 発行された `https://<owner>.github.io/<repo>/` を [tools/serve.ps1](tools/serve.ps1) の
   `$DefaultPagesUrl` に書く

GitHub Pages を使うのは、**`index.wasm`（約38MB）をそのまま置けるから**。
Cloudflare Pages / Workers 静的アセットは1ファイル25MiBまでという上限があり、
このプロジェクトの wasm はそれを超えるため配置できない。

GitHub Pages 側でビルドしないのは、Godot 本体と 1.2GB の export テンプレートが要るため。
`web-build` を毎回 force push で作り直すのは、履歴に積むとリポジトリが膨らむから
（常に1コミットしか持たない）。

itch.io ではなく Pages を使うのは、**URL クエリを自分で使えるから**。
下の参加リンクが成立するのは Pages 側だけで、itch.io は iframe 埋め込みのため
クエリが届かず、友達に「このアドレスを入力して」と伝える手間が残る。

手元でビルドを確認したいときは（`export_presets.cfg` の Web プリセットを使う）:

```sh
godot --headless --export-release "Web" export/web/index.html
python -m http.server 8123 --directory export/web
# http://localhost:8123/index.html?s=127.0.0.1 で自動参加を確認できる
```

### 遊ぶたびの手順

1. Godot でゲームを起動して **HOST**
   （[network_manager.gd](autoload/network_manager.gd) の `setup_peer()` が
   listen 成功と同時に `tools/serve.ps1` を裏で自動起動し、別ウィンドウで
   トンネルが張られる。手動で `pwsh tools/serve.ps1` を実行する必要は無い。
   Windows デスクトップ版限定で、pwsh/cloudflared が無ければそのウィンドウに
   エラーが出るだけでゲーム側は止まらない）
2. 開いた PowerShell ウィンドウに表示された参加リンク（クリップボードにコピー済み）を友達に送る

   ```text
   https://<owner>.github.io/<repo>/?s=xxxx.trycloudflare.com
   ```

3. 友達はリンクを開くだけで自動的に参加する（`?s=` を [scenes/main.gd](scenes/main.gd) が読む）
4. 全員揃ったらホスト画面で Enter

`?s=` が無ければ従来どおりロビーが出る。入力欄は IP でもホスト名でも受け付け、
[network_manager.gd](autoload/network_manager.gd) の `resolve_url()` が
**IP なら `ws://IP:9999`、ホスト名なら `wss://host`** に振り分ける。

### 既知の制約

- **トンネルの URL は起動ごとに変わる**（無料の quick tunnel のため）。毎回リンクを
  送り直すことになる。固定したいなら独自ドメイン + named tunnel（年1,500円程度）
- quick tunnel は Cloudflare が「本番用ではない」としているもので、稼働保証は無い
- **チート対策は無い**。位置の権威はクライアント側にあるので、改造クライアントは
  瞬間移動できる。`GameManager.request_drop` も `any_peer` で回数制限が無い。
  身内で遊ぶ前提の設計
- ホストPCを落とすとゲームも終わる（専用サーバではない）

バランスの要は2つ。

**追跡**は CPU の `SPEED = 8.2`。逃走者の持続平均速度（約 8.65 m/s）よりわずかに遅く、
歩行（7.0）より明確に速いので、スタミナ管理が上手ければ引き離せ、怠ると詰められる。

**探索**は `SIGHT_RANGE`（48m）と `SOLO_CPU_COUNT`（6）。この2つが「見つかるかどうか」を
ほぼ決めるが、**実際に面白い値はプレイして決めるしかない**。`SIGHT_RANGE` は
±10m で探索効率が約±20%動く最も感度の高いパラメータ。きついと感じたら
まず `SOLO_CPU_COUNT` を 5 に戻すのが安全（CPU の速度は追跡側の値なので触らない）。

## UI が英語表記な理由（日本語化する場合）

Godot 4 標準フォントに日本語グリフがなく、**Web エクスポートでは OS フォントへの
フォールバックも使えない**ため、ブラウザで日本語が「□（豆腐）」になる。日本語化するには:

1. [Noto Sans JP](https://fonts.google.com/noto/specimen/Noto+Sans+JP) の .ttf を `ui/` に置く
2. [ui/pop_theme.tres](ui/pop_theme.tres) の `default_font` に指定
3. 各 `.gd` / `.tscn` 内の UI 文字列を日本語に置換

## マルチプレイの権威モデル（改造時の注意）

- プレイヤーの位置は**各クライアントが権威**を持つ。
  速度・スタミナ・バフは同期していない
- 同期されるのは `position` / `rotation` **そのものではなく `sync_position` / `sync_yaw`**。
  権威ピアが毎物理フレームここへ書き、他ピアは `_follow_sync()` で
  **ボディごと**補間する（20Hz 同期 + exp 減衰）。インターネット越しでは到着間隔が
  ばらつくので、同期値を直接 `position` に入れるとその揺らぎがそのまま見える。
  遠い時（5m 超）は補間せずスナップする＝テレポートやマンホールワープで画面を横切って滑らない
  - **メッシュだけでなくボディを動かす**のは、視界判定とタッチ判定がどちらもボディ基準だから。
    見た目と判定がずれない代わりに、判定は最大 50ms ほど過去の位置に基づく（全員一律）
  - `_physics_process` 末尾の `sync_position = position` を消すと、
    **他ピアからそのキャラが完全に静止して見える**
  - 向きはヨーだけ同期する。ボディの x/z 回転は誰も触らないし、Euler をそのまま
    lerp すると ±PI をまたぐ瞬間に一回転する
- **スポーン時の位置は `add_child` より前に `sync_position` へ入れる**（`world.gd`）。
  レプリケートされるのは `position` ではないので、入れ忘れると他ピアでは原点に出る。
  置き物（バナナ・設置ブロック）も同じ理由で、動かないが
  `spawn = true` だけの `SceneReplicationConfig` を持たせてある
- そのため、ギミックの効果は必ず「そのボディの権威ピア」で適用する
  （`if body.is_multiplayer_authority()`）。移動結果は位置同期で他ピアへ伝わる
- 例外は **？ブロック**。抽選結果を全ピアで一致させる必要があるのでホストが決めて RPC で配信する
- タッチ判定はホストが一元的に行う。サーバは全ボディの複製コピーを持つので、
  そこで Area3D の重なりを判定している
- 動く床の位相は `GameManager.world_time`（ラウンド開始で全ピア同時にリセット）から求める。
  物理 delta は全ピアで固定値なので、以後もずれない
- **視界判定はホストが一元的に行う**。CPU 側で個別にレイを飛ばさない
  （`GameManager.hunter_sees_runner()` に問い合わせる）
- 視線の向きは**カメラではなくボディの -Z**。`player.tscn` が同期するのは
  `position` と `rotation` だけで、カメラは同期されないため、サーバがリモートの鬼の
  向きを知る手段はボディのヨーしかない。**ヨーをボディから外すとこの仕組みは静かに壊れる**
- 共有情報の代入と `spotted_changed` の発火は必ず `_set_intel` に通す。
  `_update_sight` で直接 `spotted` を書き換えると、`call_local` の RPC が
  「変化なし」と判断してホスト側だけシグナルが飛ばなくなる（ソロモードでは
  ホストが逃走者なので、SPOTTED 警告が一切出なくなる）
- マンホールの「近道か」の判定は**逃走者ではなく CPU の現在の目的地**を基準にする
  （`get_ai_goal()`）。逃走者を基準にすると、位置を知らないはずの CPU が
  逃走者に引き寄せられる抜け道になる
- 設置ブロックは Platform レイヤー(8)なので**ナビメッシュに焼かれない**。
  CPU は経路探索では避けられないので、`cpu_hunter.gd` のスタック検知
  （一定時間ほとんど進めていなければ横へ迂回）が抜け道になっている
