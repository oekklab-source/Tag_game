# セキュリティ上の既知の制約（文書化して受容）

`feature/AddCostume` → `main` の横断レビューで洗い出した所見のうち、対策を入れずに
**意図的に受容する**制約をここにまとめる。「気づいていない」のと「気づいた上で許容している」を
区別するための文書。新しく気になる点を見つけたら、まずここに同種の記載が無いか確認すること。

## 1. ジェム残高はローカル権威で改造可能

`autoload/purchase_manager.gd` が管理するジェム残高は `user://` 配下のローカル保存が正であり、
サーバ側の残高台帳は存在しない。セーブファイルを直接書き換えれば残高を増やせる。

**受容理由**: ジェムは対戦の勝敗やレーティングに一切影響しない見た目用の消費アイテム（コスチューム・帽子）
の購入にしか使わない。改造してもゲームバランス・他プレイヤーへの実害が無い。サーバ台帳を持つ設計は
コストに見合わない。

## 2. プレイヤー位置はクライアント権威

`scenes/player.gd` の位置・速度はクライアント側が権威を持ち、サーバは検証しない。
改造クライアントは壁抜け・瞬間移動などが可能。

**受容理由**: 対戦の勝敗を決めるタッチ判定自体はホストが `TagArea` の衝突で判定するため、
「触れた/触れていない」の最終判定はホストの空間上で行われる。位置チートは体験を損なうが、
不正にレートを得る決定的な手段にはならない。サーバ権威の物理は本プロジェクトの規模に対して
実装・保守コストが見合わない。

## 3. ペナルティ報告対象の PUID はホストの自己申告

`autoload/game/host_migration.gd`・`autoload/network_manager.gd` がホスト(または生存者)経由で
`rating-api` の `/report-disconnect-penalty` に送る対象 PUID は、`peer_profiles` に入った
クライアント自己申告の値をそのまま使う（C-03 R-5で旧 `service/friend-api` の `/report-penalty`・
`/consume-penalty` から統合、対象PUIDが自己申告のままという制約自体は変わらない）。
EOS Connect ID Token 認証（`autoload/rating_backend_client.gd` →
`service/rating-api/src/index.ts` の `verifyIdToken()`）により
**「誰がこのリクエストを送ったか」は保証される**が、**「送信者が名乗った対象PUIDが実在の対戦相手か」**
はサーバ側では検証できない。改造クライアントが他人のPUIDを騙ってペナルティを送りつける経路は残る。

**軽減策（実装済み）**: `rating_delta` を `-64〜-1` に制限し、報告者PUID単位で20件/日のレート制限を掛け、
さらに **被害者PUID単位でも1日あたりの減点量を合計 -64Pt（＝最大ペナルティ1回分）に制限している**
（[service/rating-api/src/index.ts](../service/rating-api/src/index.ts) の
`DISCONNECT_PENALTY_TARGET_BUDGET_PER_DAY`。上限到達後は `reason:"target_daily_cap"`）。
また `rating_before` はサーバー側D1の権威値を使うため、結果自体の改ざん（架空のPUIDに対する
「減点」を装って自分の順位を相対的に上げる等）はできない。

> **2026-09-24（C-03 R-10）の修正経緯**: 被害者単位の上限が入る前は、報告者単位の20件/日だけが
> 唯一の歯止めだった。旧 `service/friend-api` は `penalty:<puid>` というKVキーを上書きする方式で、
> 同一被害者への連投が自然に1件へ収束していたが、R-5でそのdedupを「4値から導出する決定的match_id」へ
> 置き換えた時点で **同じ被害者に別IDのペナルティを積み増せる状態**（1アカウントあたり最大
> 20件×-64Pt/日）になっていた。ここの軽減策の記述もその退行を反映しないまま残っていたため、
> R-10で実装・記述ともに直した。

**軽減策（実装済み・付随する既知の制約）**: 対象PUID・役割(runner/hunter)・**時間バケツ(5分)**
の3値から `match_id` をサーバー側で決定的に導出する（v2形式。ホスト自身が切断した場合、生存者全員が
独立に同じイベントを報告しうるため、その全員が必ず一致する値だけでdedupする。バケツ境界を
またいだ報告を取りこぼさないよう現バケツと1つ前のバケツの2点で照合している。詳細は
`service/rating-api/README.md`「既知の制約・残存リスク」参照）。**material に攻撃者が自由に
変えられる値（hunter数・自己申告rating）を含めていたv1は、リクエストごとに別IDを作って
ペナルティを積み増せたためR-10で廃止した。** 代償として、同一人物が同じ役割のまま5分以内に
複数回切断した場合は2回目以降が黙って重複排除される（1ラウンド180秒なので実害は小さい、
意図的な仕様。fail-safeの向きは「稀にペナルティが漏れる」側のみで公平性を損なわない）。

**受容理由**: サーバが対戦の存在自体を把握していない（EOSロビーはP2P、対戦結果をサーバに逐一報告する
設計ではない）ため、対象の正当性を完全に検証するには対戦セッションをサーバ側に持たせる大改修が必要になる。
現状のプレイヤー規模に対して過剰投資。

## 4. EOSロビーへの参加に認可トークンが無い

ホストの Cloudflare Tunnel 名（`*.trycloudflare.com`）は PublicAdvertised な EOS ロビー属性 `host_addr`
に載る（[autoload/eos_manager.gd](../autoload/eos_manager.gd)）。ロビーを列挙できる誰でも、
ロビーに実際に入らず直接 `wss://` で接続を試みることができる。合言葉やトークンによる join 認可は無い。

**受容理由**: 接続できても `PROTOCOL_VERSION` 不一致やゲームプロトコルを話せないクライアントは
弾かれる。トンネル名自体はランダムかつ短命（ホスト起動のたびに変わる）なので、総当たりでの発見コストも
低くない。友人内対戦を主用途とする現状の規模で、追加の認可機構を持つ投資対効果は低いと判断した。

## 5. フレンド検索(表示名の完全一致)は本人から名前を直接聞いた以上の特定手段になる

`service/friend-api/src/index.ts` の `/search-user`(`mode=name`)は、表示名の完全一致で
相手のフレンドコードを取得できる。KVの `get()` は完全一致lookupしかできず前方一致・部分一致・
一覧列挙は構造的に実装できないため、総当たりでの他人の存在確認や名前一覧の収集は防げているが、
「正確な表示名を知っている」相手についてはコードを特定できてしまう。

**受容理由**: 表示名は本人がゲーム内で名乗っている値であり、他人から聞く・画面越しに見る等で
知り得る情報の範囲を超えない。フレンド追加前のプレビュー用途としてユーザー側の要望で追加した
機能であり、列挙攻撃(総当たりでの発見)への対策は`/search-user`の構造自体で維持されている。

## 6. フレンドの戦績・レート・スキン(`stats:<puid>`)は自己申告で未検証

`/sync` の `stats` フィールドはクライアントの自己申告のままサーバーに保存され、`/friend-profile`
経由でフレンドに公開される。改造クライアントは任意の値(異常なレート・戦績)を送れる。

**受容理由**: この値は実際のレート計算(`autoload/ranking_manager.gd`)や`rating-api`(D1)・
EOS Leaderboards(レガシー経路)のいずれにも一切使われず、フレンド同士の参考表示にしか使わない。
フレンドにしか見えないうえ対戦結果・マッチングに影響しないため、既存の「1. ジェム残高はローカル権威」
と同種の実害が小さい受容リスクと判断した。

## 7. ランクマッチの結果報告はホスト単独（報告者自身が参加した「架空の試合」は防げない）

C-03でランクマッチの結果報告(`autoload/game/rating_report.gd`経由の`/report-match`)を
ホスト単独で行う設計(Option A)を採用した。サーバー(`service/rating-api`)は「その試合が
実在したか」自体を検証する手段を持たない構造的限界がある。項目3(切断ペナルティの
PUID自己申告)と同種の信頼モデルである。

**軽減策（実装済み、C-03 R-10）**: 報告者PUID(EOS Connect ID Tokenで保証される)が、
報告された参加者一覧`[runner_puid, ...hunter_puids]`に**含まれていること**を必須にした
(`isReporterParticipant()`、外れると`reason:"reporter_not_participant"`)。これにより
**「全く無関係の他人同士の試合をでっち上げて、任意PUIDのレートを一方的に動かす」経路は塞がった**。
`/leaderboard-top`が上位N件のPUIDを認証なしで列挙できる(項目8)ため、この検証が無い状態は
攻撃の実行コストが極めて低かった。

**残る穴（受容）**: 報告者が**自分自身を参加者に含めた**架空の試合は依然として報告できる。
1アカウントだけでも「自分がrunner・狙った相手がhunter」という試合を作れるため、
特定PUIDのレートを削る／自分のレートを吊り上げる行為は成立する。被害上限は
`MATCH_REPORT_LIMIT_PER_DAY`(150件/日・報告者PUID単位、実プレイで到達しうる上限に
合わせて2026-09-24に300から引き下げ)のみ。

**受容理由**: 完全に塞ぐには「報告された参加者が本当に同じEOSロビーに居たか」をサーバーが
検証する必要があり、対戦セッション自体をサーバー側に持たせる大改修（ロードマップC-03 R-0の
EOS投資判断待ち）になる。現状のプレイヤー規模に対して過剰投資。README「マルチプレイの権威モデル」
節が定める「タッチ判定はホストが一元的に行う」という既存の信頼モデルの自然な延長でもある。

## 8. `/leaderboard-top` はPUIDを認証不要で列挙可能

`service/rating-api`の`/leaderboard-top`は公開ランキングという性質上、上位N件のPUIDを
認証なしで一括列挙できる。`service/friend-api`は「PUIDそのものは公開しない」ことを設計原則と
しているため、この点は原則と衝突する。それでもPUIDを含めているのは、(1)自分の順位ハイライト
表示で同率レート下の本人特定に必要、(2)将来のランキング画面での名前解決join keyとしても
使う可能性があるため。

**受容理由**: PUID単体を知っているだけではフレンド追加も接触もできない
(`service/friend-api`のフレンド追加は8桁コード経由のみ)ため、実害は小さいと判断した。
ただし項目7の「報告者=参加者」検証が無い間は、ここで得たPUID一覧がそのまま攻撃対象リストに
なっていた(C-03 R-10で解消)。

## 9. `/claim-initial-rating` はレートの自己申告を受け入れる唯一の窓口

`service/rating-api`の`/claim-initial-rating`は、サーバー権威化(C-03)より前から遊んでいた
プレイヤーのローカルレートをD1へ引き継ぐための移行用エンドポイントで、値はクライアントの
自己申告をそのまま初期値にする(検証する手段が無い)。

**軽減策（実装済み、C-03 R-10）**:
- 受付上限を既定値の **1500** に下げた（自己申告では既定値より上を名乗れない＝移行では
  「下げる方向のみ」許す）。以前は2500まで受け入れており、新規アカウントがいきなり
  公開ランキング上位に居座れた。
- `seeded_from_client = 1` の行（＝claim経由で作られた行）は、`matches_played` が5件に
  達するまで `/leaderboard-top` から除外する。この列はR-2で監査用に用意したまま
  どのクエリも読んでいなかったが、ここで実用途がついた。ratings行はすべてclaim経由で
  作られるため、実質「ランクインには5試合必要」という配置マッチ相当の仕様になる
  （`/rating` は除外しないので本人のプロフィール表示には影響しない）。
- 1行目のINSERT失敗そのものを「claim済み」の判定に使っているため、2回目以降のclaimは
  `already_claimed` になる（値の上書きはできない）。

**受容理由**: 1500以下の自己申告は引き続き無検証で通る。実害は「本来もっと低いレートの
プレイヤーが1500から始められる」程度で、その後の試合はすべてサーバー権威の再計算に
従うため、上位帯の汚染には繋がらない。
