# 非対称型3D鬼ごっこ Elo レーティング計算モデル仕様書

## 1. 概要と課題背景

本ゲームは **1人の逃走者 (Runner) vs 複数人の鬼 (Hunter)** による非対称型オンライン対戦ゲームです。

### 課題
1. **1 vs N の非対称性**: 参加人数の増減（2〜8人）によって逃走側の生存難易度が劇的に変動する。
2. **勝敗の連続性（試合時間）**: 制限時間3分（180秒）に対し、開始直後に捕まるのと終了間際まで逃げ粘るのとでは、同じ「Hunter勝利」でも双方のパフォーマンス（貢献度）が異なる。
3. **チーム内の貢献度格差**: 索敵・追い込みを担当したHunterと、実際に物理接触（タッチ）してトドメを刺したHunterの評価分配。
4. **レートのインフレ/デフレ防止**: 非対称なマッチングを繰り返しても、全体のレート総量が自然に維持されるゼロサム性（保存則）。

---

## 2. 数理モデル設計

### 2.1 試合時間依存スコア算出 ($S$)
試合結果を $0$ または $1$ の離散値ではなく、生存時間 $T$ (0〜180秒) に応じた連続的なスコアとして定義します。

- **Runner のスコア ($S_R$)**:
  $$S_R = \begin{cases} 0.5 \times \left( \frac{T}{180} \right) & (T < 180 \text{秒 : 捕獲}) \\ 1.0 & (T = 180 \text{秒 : 逃げ切り完全勝利}) \end{cases}$$
- **Hunter 陣営のスコア ($S_H$)**:
  $$S_H = 1.0 - S_R$$

> **設計意図**:
> - 捕まった場合でも、長く生き残るほど最大 0.5（引き分け相当）までスコアを獲得可能。
> - 鬼側は早期に捕獲するほど $1.0$ に近い高スコアを獲得。

---

### 2.2 非対称ゼロサム Kファクター
全体のレート総量を保存（ゼロサム）させるため、$K_R = N \times K_H$ の関係を人数スケーリングで成立させます。

- 基準係数: $K_{base} = 16.0$
- **Runner の Kファクター**: $K_R = K_{base} \times \sqrt{N}$
- **Hunter の Kファクター**: $K_H = K_{base} / \sqrt{N}$

---

### 2.3 参加人数ハンディキャップ補正
標準人数（Hunter 4人）を基準とし、鬼の人数 $N$ に応じて仮想レート補正 $O(N)$ を適用します。

$$O(N) = 50.0 \times (N - 4)$$
$$R_H^* = \left( \frac{1}{N} \sum_{i=1}^N R_{Hi} \right) + O(N)$$

- **Runner の期待勝率**:
  $$E_R = \frac{1}{1 + 10^{(R_H^* - R_R) / 400}}$$
- **各 Hunter $i$ の期待勝率**:
  $$E_{Hi} = \frac{1}{1 + 10^{(R_R - (R_{Hi} + O(N))) / 400}}$$

---

### 2.4 レート変動値 ($\Delta R$) と完全ゼロサム誤差補正

1. **基本変動値の計算**:
   $$\Delta R_R = K_R \times (S_R - E_R)$$
   $$D_{Hi} = K_H \times (S_H - E_{Hi})$$

2. **誤差プール補正（ゼロサムの厳密担保）**:
   ロジスティック曲線の非線形性による端数ズレを吸収するため、誤差を Hunter 全員に均等配分します。
   $$\text{Error} = (-\Delta R_R) - \sum_{i=1}^N D_{Hi}$$
   $$D_{Hi} \leftarrow D_{Hi} + \frac{\text{Error}}{N}$$

---

### 2.5 トドメ（タッチ）貢献度再分配

Hunter 陣営が勝利しレート獲得（プラス変動）が発生した場合のみ、協力者から一定割合をトドメ役に還元します。

- 移転比率: $\beta = 0.3$ (30%)
- トドメ以外の Hunter $j$ で $D_{Hj} > 0$ の場合:
  $$\text{Transfer}_j = D_{Hj} \times 0.3$$
  $$D_{Hj} \leftarrow D_{Hj} - \text{Transfer}_j$$
  $$D_{\text{Toucher}} \leftarrow D_{\text{Toucher}} + \sum \text{Transfer}_j$$

### 2.6 低レート帯ボーナス（序盤は純増、上位帯はゼロサム）

2.4節の誤差プール補正と2.5節のトドメ再分配で作った値は変更せず、**その後に**低レート帯向けのボーナスを加算する。挿入位置が前後すると成立しなくなる。

- **誤差プール補正より後でなければならない理由**: 補正より前にボーナスを乗せると、2.4節の誤差プール計算がボーナス込みの値を「誤差」とみなして打ち消してしまい、ボーナスが消える。
- **トドメ再分配より後でなければならない理由**: ボーナスは「参加報酬」であり、2.5節のトドメ移転（協力者からトドメ役へ30%移転）の対象になるべきではない。

$$w(R) = \begin{cases} 1.0 & (R \le 1400) \\ \dfrac{1800 - R}{1800 - 1400} & (1400 < R < 1800) \\ 0.0 & (R \ge 1800) \end{cases}$$

$$b(R, S) = B_{max} \times w(R) \times \left(1 + \tau \times (1 - S)\right) / |\text{陣営人数}|$$

- $B_{max} = 6.0$（満額時、Runner1人が受け取る基準ボーナス）
- $\tau = 0.5$（負けた側＝スコア $S$ が低い側を厚くする係数。連敗で沈むのを防ぐ）
- 判定基準は **参加者の平均レートではなく各プレイヤー個別のレート**。平均基準だと高レート帯に紛れた初心者が救済されない上、高レート部屋に低レート者を1人混ぜて全員分のボーナスを錬成する悪用が成立してしまうため。

$$\Delta R_R \leftarrow \Delta R_R + b(R_R, S_R)$$
$$D_{Hi} \leftarrow D_{Hi} + b(R_{Hi}, S_H)$$

$w(R)=0$（$R \ge 1800$、[5節](#5-レート帯ティア定義)のダイヤ以上）では加算量が0になり、**2.1〜2.5節のみで計算した従来の完全ゼロサムと1ptも変わらない**。実装は `calculate_all_rating_changes(..., apply_bonus: bool = true)` の `apply_bonus=false` で本節を無効化でき、既存テストのリグレッション確認に使っている。

## 6. 適用範囲・既知の制約

- **VS CPU戦には適用しない**: `GameManager.round_is_ranked` が真（オンライン対戦かつ人間の対戦相手が1人以上）のときのみ `RankingManager.apply_match_end()` を呼ぶ。ソロ練習（CPU戦）ではレート・戦績とも変動しない。
- **レートはクライアント側の自己申告**: `user://profile.json` にローカル保存されるのみで、サーバー側の検証は無い。書き換えによる詐称（低ティアに居座って低レート帯ボーナスを稼ぐ等）は現状の実装では防げない。将来サーバー権威化する場合は `ProfileManager.merge_server_inventory()` 相当の仕組みで上書きできるようにする。
- **各クライアントが自分の取り分だけを独立計算する**: レート変動値はRPCで同期されず、Runner/Hunterそれぞれが `calculate_rating_delta()` を自分の端末でローカルに呼ぶ。そのため、同一の試合結果（例: 逃げ切り）に対してRunner側とHunter側で異なる `survival_time` を渡すと評価が食い違う恐れがある。`calculate_rating_delta()` は `is_runner == is_winner`（逃げ切り）の場合に `survival_time` を必ず `MAX_TIME` へ正規化することで、Runner視点・Hunter視点のどちらで計算しても同じ `sr=1.0 / sh=0.0` になることを担保している（回帰テスト: `tests/rating_model.gd` の `test_clean_escape_symmetric_across_clients()`）。

## 7. コード構成と呼び出し方法

- **コア実装**: [autoload/ranking_manager.gd](file:///c:/sandbox/Tag_Game/autoload/ranking_manager.gd)
  - `calculate_all_rating_changes(...)`: 全員分のレート変動を一括算出（`apply_bonus`で2.6節のボーナス有無を切替）
  - `calculate_rating_delta(...)`: 単一プレイヤー用のラッパー
  - `apply_match_end(...)`: 試合終了時に ProfileManager / EosManager へ自動反映
  - `tier_index(...)` / `tier_id(...)` / `tier_name(...)` / `tier_color(...)` / `is_rating_compatible(...)`: レート帯（ティア）判定
